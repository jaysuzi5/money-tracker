Money Tracker

A self-hosted Quicken replacement · Django + PostgreSQL on local k8s

Plan v0.2 · 2026-06-26 · status: DECISIONS LOCKED — building

Goal: replace a 20-year Quicken habit with a self-owned app you control — no subscription, reports tailored to you, data 100% local in PostgreSQL. The make-or-break feature is automatic daily data pull from your financial institutions with no manual download/upload. This plan recommends a connection strategy, a data model that handles your envelope/"dummy" sub-accounts and hierarchical categories, and a deployment that mirrors the existing vacation-planner app.

1. Goals & non-goals

Goals

  • All data local in PostgreSQL on your k8s cluster.
  • Automatic daily pull from all institutions — zero manual file shuffling.
  • Per-transaction detail + reconciliation for Discover and PSECU checking.
  • Balance + holdings tracking for investment/retirement accounts.
  • Envelope sub-accounts (allowances, sinking funds).
  • Configurable hierarchical categories (Utilities → Electric).
  • Transfers between accounts.
  • Custom reports / net worth over time.

Non-goals (v1)

  • Bill pay / moving money (read-only aggregation only).
  • Multi-user SaaS — single household, you + wife.
  • Tax-lot accounting / cap-gains optimization.
  • Mobile native app (responsive web is enough; PWA like vacation-planner).
  • Replicating every Quicken report — build the few you actually use.

The connector framework is a pluggable interface: each connector returns a normalized list of accounts, balances, holdings, and transactions. The sync engine upserts them and runs the matcher. This means you can start with SimpleFIN for everything and swap individual institutions to a scraper later without touching the rest of the app.

5. The hard part: getting the data

This is the deciding feature. Three viable approaches, in order of recommendation.

Option A — SimpleFIN Bridge RECOMMENDED PRIMARY

What it is

A privacy-first aggregation service built for personal-finance apps (it's what Actual Budget uses). You log into each institution once on SimpleFIN's site; it hands your app a single read-only access token. Your app polls a REST endpoint for accounts, balances, and transactions.

  • Cost: ~$1.50/mo or $15/yr — flat, not per-call.
  • Cadence: refreshes ~once/24h — matches your daily goal exactly.
  • Read-only by design; can't move money.
  • You never store bank passwords — only a SimpleFIN token (encrypted at rest).
  • Covers Fidelity (Plaid does not — see Option B), brokerages, banks, credit unions, cards.

Why it fits you

  • Daily-pull model is literally its design point.
  • Handles MFA on its side during the one-time link — you're not building MFA automation.
  • Cheapest path; replaces a Quicken subscription with a near-zero fee.
  • One integration covers all 5 logins if all are supported.

Risks

  • Verify coverage for PSECU, Wealthfront, Discover, both Fidelity logins before committing.
  • Transaction granularity for credit-union checking can vary — confirm Discover & PSECU give per-transaction detail (they generally do).
  • Periodic re-auth when an institution forces it (handled via a UI "re-link" prompt).
Recommendation: Build the SimpleFIN connector first. Before writing code, create a free SimpleFIN account and confirm each of your 5 institutions links and returns the detail you need. This single check de-risks the whole project.

Option B — Plaid SECONDARY / SELECTIVE

  • Best-in-class coverage and clean categorized data but Fidelity does not use Plaid — a hard gap for your 8 Fidelity accounts.
  • Production access requires an approval process; pricing is per-item/per-call and oriented at businesses, not hobbyists.
  • You'd hold Plaid access tokens; data flows through Plaid infra (less private than SimpleFIN).
  • Reasonable only as a fallback for a specific institution SimpleFIN can't do well — and not for Fidelity.

Option C — Browser-automation scraping (Playwright) FALLBACK ONLY

An "agent" that logs into each site in a headless browser and scrapes. Full control, no third party, but real costs:

Pros

  • Works for any site, any field, full transaction detail.
  • No per-account fees beyond compute.
  • No third party sees your data.

Cons

  • MFA is the killer — most accounts force 2FA; automating it is fragile.
  • You must store bank passwords (encrypted) — bigger blast radius.
  • Breaks whenever a site changes layout; ongoing maintenance.
  • May violate institution Terms of Service; risk of lockouts/captcha.
MFA handling pattern (if you ever need a scraper): store a persistent browser profile / session cookies per institution so re-login is rare; where the bank offers an app-specific or read-only password, use it; for live OTP, have the scraper pause and send you a push notification, you enter the code in the UI, the scraper resumes. Treat this as a per-institution last resort, not the default.

6. Sync agent design

Connector interface

class Connector(Protocol):
    def fetch(self, credential: ConnectionCredential) -> SyncResult: ...

# SyncResult is normalized, source-agnostic:
@dataclass
class SyncResult:
    accounts:     list[NormAccount]      # external_id, name, type, balance, currency
    holdings:     list[NormHolding]      # account_ext_id, symbol, qty, price, value
    transactions: list[NormTxn]          # account_ext_id, ext_id, date, amount, payee, memo

Implementations: SimpleFinConnector (v1), PlaidConnector / PlaywrightConnector (later). The sync engine doesn't care which produced the data.

Sync engine flow (per run)

manage.py sync_accounts [--institution X] [--since DATE]
  for each active ConnectionCredential:
    result = connector.fetch(credential)
    upsert accounts (match on external_id)
    snapshot balances  -> BalanceSnapshot (one row/account/day)
    replace holdings    -> Holding (investment accounts)
    for each txn:
       dedupe on (account, external_id)        # idempotent re-runs
       insert as status=IMPORTED, cleared=True
       run matcher against manual UNCLEARED txns
    write SyncRun row (counts, errors, duration)  # audit, like vacation-planner logging
  • Idempotent: external transaction IDs prevent duplicates on re-sync.
  • Scheduled: k8s CronJob daily ~06:00 (mirrors backup CronJob pattern) running the management command.
  • On-demand: a "Sync now" button in the UI triggers the same command for a single institution.
  • Observable: every run logged + OTEL span + a SyncRun record visible in the UI (last-synced badge per account).

8. Envelope / "dummy" sub-accounts

Your "dummy" accounts (Self/Wife allowances inside PSECU checking; the 10 sinking funds inside the Wealthfront Cash Account) are virtual partitions of a real account's balance, not separate bank accounts. Modeled as Bucket rows under their parent Account.

Behavior

  • Parent account's real balance = source of truth (from sync).
  • Each bucket holds an earmarked portion; sum of buckets ≤ parent balance.
  • An "unallocated" remainder = parent balance − Σ buckets is shown so nothing hides.
  • Moving money into/out of a bucket is an internal allocation (a Transaction tagged with a bucket, or a dedicated BucketTransfer) — it does not change the parent's real balance, only the split.

This mirrors envelope budgeting (YNAB/Actual). When a real transaction hits the Cash Account from the bank, you assign it to a bucket during reconciliation — same gesture as assigning a category.

9. Receipt logging & reconciliation

Your daily workflow, preserved: log receipts as you spend, then match incoming bank transactions.

1. SPEND → you log a receipt → Transaction(source=manual, status=UNCLEARED) 2. DAILY SYNC → bank txns pulled → Transaction(source=imported, cleared=True) 3. MATCH ENGINE → pairs imported↔manual → on match: manual.status=RECONCILED, (amount + date window + drop the dup import (or merge memo/category) fuzzy payee) 4. REVIEW QUEUE → unmatched imports shown → you categorize / assign bucket / confirm 5. RECONCILE → per-account session → assert running balance == bank balance

Matching rules

  • Exact: same account + amount + date within ±N days → auto-match candidate.
  • Fuzzy payee: normalize merchant strings ("AMZN Mktp" ≈ "Amazon") to boost confidence.
  • Confidence threshold: high → auto-reconcile; medium → suggest in UI; low → leave in review queue.
  • Never silently delete a manual entry — merge into it so your category/memo survive.

Reconciliation screen (Quicken-style register)

Per reconcilable account (Discover, PSECU checking): a register table with a "cleared" column, a target = bank statement balance, and a running difference that must hit $0. Matches vacation-planner's CBV + Bootstrap table style.

Investment / retirement accounts skip all of this — they only get daily balance + holdings snapshots.

10. Categories

  • Self-referential Category: a parent (Utilities) with children (Electric, Gas, Water).
  • Fully configurable in the UI / admin — add, rename, deactivate; pick from existing on each transaction.
  • Seed with a sensible default tree (mirror your current Quicken categories) via a data migration.
  • Optional auto-categorization: remember "payee X → category Y" so repeat merchants pre-fill.
  • Reports roll up by parent or drill into subcategory.

12. Security & secrets

This app holds your entire financial picture. Treat it accordingly.
  • Prefer no stored bank passwords — SimpleFIN means you store only a read-only token. This is the single biggest security win and a reason to avoid scraping.
  • Encrypt all credentials/tokens at rest with Fernet (cryptography lib). The Fernet key lives in a SealedSecret, injected as env var — never in the DB or git.
  • SealedSecrets for everything sensitive (DB creds, SECRET_KEY, SimpleFIN token, Fernet key, AWS keys) — same pattern as vacation-planner.
  • Auth: Google OAuth via allauth; restrict to your + wife's accounts; all querysets user-scoped (OwnerRequiredMixin pattern).
  • Network: Cloudflare TLS termination, secure cookies, HSTS — copy vacation-planner settings.
  • Read-only posture: the app never initiates money movement. No write access reduces worst-case blast radius to data exposure, not theft.
  • Backups encrypted in transit/at rest; the S3 backup bucket already exists in your pattern.
  • Audit: SyncRun + page logging middleware give you a trail of every data pull.

16. Quicken QIF historical import

One-time (repeatable) importer for 20 years of history from two Windows Quicken QIF exports.

QIF format primer

  • Plain text. Sections start with !Type:Bank / !Type:CCard / !Type:Cash / !Type:Invst; account list under !Account; categories under !Type:Cat.
  • Each txn = lines keyed by leading char, ended by ^: D=date, T=amount, P=payee, L=category/transfer ([Account] = transfer), M=memo, C=cleared status, S/E/$=split lines.
  • Investment (!Type:Invst): N=action (Buy/Sell/Div), Y=security, Q=qty, I=price.

Importer design

manage.py import_qif <file.qif> --institution <name> --account-map map.json [--dry-run]
  parse QIF → sections
  upsert Categories from !Type:Cat (merge old/new differing trees)
  for each account section:
     resolve/create Account (via --account-map: QIF acct name → our Account)
     for each txn:
        build NormTxn; L "[Acct]" → mark as Transfer
        dedupe key = (account, date, amount, normalized_payee)   # old+new file overlap
        if exists → skip (or update memo/category if richer); else insert source=imported_qif
     splits → child category allocations
  report: inserted / skipped-dup / unmapped-category / unmapped-account   # always print, dry-run first
  • Dedup across the two files on (account, date, amount, payee) so the overlapping period doesn't double up. --dry-run prints counts before committing.
  • Category reconciliation: old and new Quicken may name categories differently — importer emits an "unmapped/uncertain" list; you map via a small JSON, re-run idempotently.
  • Account mapping: QIF account names → your Account rows via --account-map JSON (handles renamed accounts across the 2 files).
  • Idempotent: safe to re-run; dedup key prevents duplicates. Order: old file first, then current file.
  • Historical imports tagged source=imported_qif so they're distinguishable from live SimpleFIN data and never re-matched by the daily reconciler.
